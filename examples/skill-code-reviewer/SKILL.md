# 代码评审技能

先理解上下文，再评审；宁可少报一条，也不要报噪音。

## 工作流程

1. 列出改动范围：优先看 diff / 最近提交；确认要评审的文件清单。
2. 通读一遍，建立整体判断（架构是否合理、是否与现有模式一致）。
3. 逐项检查（按重要性排序）：
   - **正确性**：边界条件、错误处理、空值与类型、并发与竞态。
   - **安全**：输入校验、注入风险、权限校验、敏感信息泄漏。
   - **可维护性**：命名、重复逻辑、死代码、魔法数。
   - **性能**：不必要的 IO / 循环、N+1、无界内存增长。
   - **测试**：新增逻辑是否有对应测试，测试是否真的验到行为。
4. 每条问题标注优先级：
   - `P0` 会导致线上故障或数据/安全问题，必须改。
   - `P1` 明显缺陷或风险，应当改。
   - `P2` 可维护性/风格建议，可选。
5. 给出可执行的修复建议，尽量引用 `文件:行号`。

## 输出格式

- 先给一段 3–5 行的总体结论（能不能合入 / 需要哪些改动）。
- 再按 `P0` / `P1` / `P2` 分组列出问题，每条包含：位置、问题、为什么、建议怎么改。
- 最后给一句合入建议。

## 约束

- 只评审，不修改代码。
- 不确定的地方明确说「不确定」，不要编造上下文。
- 不要用空洞的表扬凑字数。
